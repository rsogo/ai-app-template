# 公開する（社内公開）

前提：`AGENTS.md` の「必ず守るルール」に従う。利用者は Cloudflare の鍵を持たない。

**社内公開は申請不要。** アプリのリポジトリの `main` ブランチに送る（push）と、基盤が自動で「公開前チェック → テーブル変更の反映 → 公開」を行う。見られるのは社内でログインした人だけ。
社外への公開だけは申請制（`docs/agent/request.md`）。

> 初回は、NCDC から「新しいアプリの用意」の完了連絡（設定値）が届いてから。届いた設定値の反映は `docs/agent/request.md` の「用意ができたら」を参照。

## 公開前に確認すること

```
npm run build             # 型チェックとビルドが通ること
npm run db:migrate:local  # 新しいマイグレーションが手元で通ること
npm run check             # 公開前チェック（公開時に基盤も同じチェックを行う）
```

`npm run check` が止まったら、表示された理由を利用者に平易な言葉で伝えて直す。
- 「データが消えます」：`docs/agent/migration.md` の「データが消える変更」に従い、利用者の了承を得て印を書く
- 「鍵やトークンのような文字列」：その文字列を消し、外部連携の申請にする

あわせて、次をコードで確認する：
- SQL がすべて `bind` を使っている
- 更新・削除の API が `requireOwner` を呼んでいる
- `platform/`、`scripts/`、既存のマイグレーションファイルを変更していない

## 公開する

1. 変更内容を利用者に説明し、社内に公開してよいか確認する
2. 変更をコミットし、`main` に push する
3. 数分で反映される。結果は GitHub のコミットの横に表示される（✓ 公開済み ／ ✕ 止まった）
4. 公開 URL（`https://<アプリ名>.<サブドメイン>.workers.dev`）を利用者に伝える。URL は NCDC の完了連絡に書かれている

`wrangler deploy` や `--remote` 付きのコマンドは実行しない。公開は push だけで行う。

## 止まったとき（✕）

- ほとんどは公開前チェックで止まっている。手元で `npm run check` を実行すると同じ理由が表示されるので、直してもう一度 push する
- `npm run check` が通るのに止まる場合は、基盤側の問題。利用者に伝え、NCDC への依頼文（不具合）を作る

## 前の版に戻す

- 画面・API は前の版に戻せる。利用者の同意を得てから、直前のコミットを打ち消すコミット（`git revert`）を作り、push する
- データ（DB の中身）は戻さない。必要な場合は NCDC に連絡する（30日以内なら戻せる）
